# RAG 评估

RAG 系统，搞清楚三件事就够了：

1. 检索的准不准？
2. 生成的对不对？
3. 跑得快不快/稳不稳？

## 评估指标

量化评估，需要指标：

### 检索评估 — 检索的准不准？

1. 上下文相关性 (context relevance)

检索出来的文档碎片里，有多少是真正相关的？

2. 上下文召回率 (context recall)

标准答案里的信息，检索有没有遗漏？

### 生成评估 — 生成的对不对？

1. 忠实度（faithfulness）

答案里的每一句话，都能在检索到的文档里找到依据吗？

2. 答案相关性（answer relevancy）

生成的答案，是否直接回应了用户的问题？

### 性能评估 — 跑得快不快/稳不稳？

1. 延迟（Latency）

检索+生成全流程响应时间

2. 吞吐（Throughput）

高并发下性能稳定性

3. 缓存命中率（Cache Hit Rate）

是否重复计算

4. 可复现性（Reproducibility）

同样问题是否输出一致

5. 时效性（Recency）

知识库更新后，是否能实时反映到答案中

## 评估维度

光指标不够，得知道出问题的环节。

评估分静态和动态：静态查数据质量，动态查运行结果。

RAG 有 8 个环节：

①数据接入 → ②文档切分 → ③向量索引 → ④检索召回 → ⑤重排序 → ⑥Prompt组装 → ⑦答案生成 → ⑧引用溯源

每个环节最爱出问题的地方：

1. 数据接入 — 文档解析失败（PDF 表格丢了、图片没提取文字）
2. 文档切分 — 语义断裂（一条完整规则被切成两半）
3. 向量索引 — embedding 不适配领域（通用模型对金融术语理解差）
4. 检索召回 — 漏召回（口语化匹配不到文档）、噪声多（检回不相关的东西）
5. 重排序 — 第一阶段没召回的，重排救不了；重排本身有延迟开销
6. Prompt组装 — chunk 顺序排错了、上下文超长被截断、历史对话没拼进去
7. 答案生成 — 幻觉（编造 context 里没有的内容）、过度拒绝（能答的偏说不懂）
8. 引用溯源 — 引用的 chunk 不支持这个声明、chunk 换过了引用链接没更新

## 评估方法

### RAGAS

RAGAS 解决两个问题：

1. 生成质量可量化

faithfulness 拆 claims 逐条验证有没有编、answer relevancy 反向生成问题看对不对得上

2. 检索侧细化

context precision 看噪音、context recall 看遗漏

核心理念：用 LLM 评估 LLM，零标注成本。

使用流程：

1. 准备测试集



人工写问答对，或从文档反向生成。每条包含 question + ground_truth。

2. 跑 RAG pipeline

每个 question 过一遍系统，收集 contexts（检索结果）+ answer（LLM 生成）。

3. RAGAS 打分

输入 (question, answer, contexts, ground_truth)，四个指标自动出分，Python 几行代码的事。
