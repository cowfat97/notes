# 文档分块

## What — 是什么

文档分块把读取模块产出的 `ContentElement` 列表，按 `doc_type` 标签选择对应的切分策略，输出 `Chunk` 列表供向量化使用。

核心思路同样是**策略模式**——标题、段落、表格、图片各走不同的切分器。编排器 `SplitPipeline` 按文档区域分组分发，`ParentChildPipeline` 做两遍切分实现父子块。

```text
[ContentElement](doc_type=heading/paragraph/table_row/image)
  → SplitPipeline（按区域分组：文本区域 → 标题切分器，表格区域 → 不切，图片区域 → 不切）
  → [Chunk, Chunk, ...]（每个带 chunk_id）
```

## Why — 为什么

切分方式直接影响检索质量和 LLM 生成质量：

- **切太细** → 语义碎片化，"信用卡年费减免条件：消费满6笔"变成了两个无意义的 chunk
- **切太粗** → 关键信息被稀释，向量相似度被噪声拉低
- **切的位置不对** → 表格被拦腰切断、标题和正文分到不同 chunk
- **切分器不感知文件类型** → Markdown 的标题天然是边界，但被当成普通段落按字数切

## How — 怎么做

### 1. 整体架构：策略模式 + 区域分组

```text
SplitPipeline
  ├─ 文本区域（heading + paragraph 交插）→ HeadingSplitter / RecursiveSplitter
  ├─ 表格区域（table_row）              → NoOpSplitter（不切）
  └─ 图片区域（image）                  → NoOpSplitter（不切）
```

`SplitPipeline.split()` 的逻辑不是按 doc_type 分组——那样会把 heading 和 paragraph 拆散，导致标题切分器看不到正文。实际是按**区域**分组：连续的同 "区域类型"（文本 / 表格 / 图片）的元素合并，一次交给对应切分器。这样 HeadingSplitter 能同时看到 heading 和 paragraph，正确建立标题-正文的 section 结构。

### 2. 数据结构

```python
@dataclass
class Chunk:
    content: str                     # 切分后的文本
    doc_type: DocType                # 继承自 ContentElement
    metadata: dict                   # 透传 + 附加（标题层级、parent_content）
    chunk_id: str                    # 唯一标识
    parent_id: str | None = None     # 指向父块（子块场景）
```

### 3. 四种切分策略

#### RecursiveSplitter — 递归标点切分（默认）

按中文标点优先级递归切分，直到每个 chunk 不超过 chunk_size：

```text
分隔符优先级（从高到低）：
  "\n\n"   → 段落边界（首选）
  "\n"     → 换行
  "。" "！" "？" → 中文句末标点
  "；" ";" → 分句标点
  "，" "," → 逗号
  字符级截断 → 最后手段（单句超过 chunk_size 时）
```

核心逻辑：从最高优先级分隔符开始尝试。如果能切出多个片段 → 递归处理每个片段。如果切不开 → 降到下一级分隔符。如果全切不开 → 强制按字符截断。

chunk_overlap：末尾留一段拼入下一个 chunk 开头，避免关键信息刚好落在切断点。

#### HeadingSplitter — 标题边界切分

以 Markdown 标题 `#` 层级为切分边界。每个标题 + 其下所有正文内容构成一个 chunk。遇到同级或更高级标题时结算上一个 section。

chunk 的 metadata 带上标题信息和层级，供检索时做精确过滤：

```python
chunk.metadata = {
    "heading": "信用卡年费政策",
    "heading_level": 2,
}
```

#### MarkdownSplitter — Markdown 专用

继承 HeadingSplitter，行为一致。独立命名是为了代码中明确区分—— `.md` 文件走 MarkdownSplitter，其他文件在"文本区域"走 RecursiveSplitter。

#### NoOpSplitter — 不切分

用于 `table_row` 和 `image` 类型的元素。原样输出，不做任何切分。表格行内切分会破坏数据结构，图片 OCR 文本独立成块即可。

### 4. 父子块

**核心矛盾**的答案：子块搜，父块看。

```text
父块 1200 token（入 LLM 上下文 = 完整章节）
  ├─ 子块1 300 token ← 检索命中 → 通过 parent_id 取父块全文
  ├─ 子块2 300 token
  ├─ 子块3 300 token
  └─ 子块4 300 token
```

实现方式不是独立切两次再关联（会导致边界错位），而是**父块先切 → 每个父块内部再切子块**：

```text
elements → SplitPipeline(1200) → parent_chunks
  → for each parent:
      → RecursiveSplitter(300)(parent.content) → child_chunks
      → child.parent_id = parent.chunk_id
      → child.metadata["parent_content"] = parent.content
```

这样父子关联是确定的——子块内容一定在父块内容里，不会错位。

**为什么不是固定 300/1200**：根据文档类型动态调整。FAQ 条目短，子块可降到 100-150 token。产品文档按章节，父块可到 1500 token。切分器的最小约束是不断句——宁可块大小有偏差，也不生成半句话。

### 5. 完整切分流程

```python
# 创建切分 Pipeline
pipeline = SplitPipeline(
    text_splitter=MarkdownSplitter(chunk_size=1200)  # .md 走标题切分
)
# 或
pipeline = SplitPipeline(
    text_splitter=RecursiveSplitter(chunk_size=300, chunk_overlap=50)  # 其他走递归切分
)

chunks = pipeline.split(elements)
# → 每个 chunk 带 doc_type 和 metadata，可直接送 embedding
```

父子块流程：

```python
pc = ParentChildPipeline(parent_size=1200, child_size=300, overlap=50)
parents, children = pc.split(elements, is_markdown=True)

# parents  → 不入向量库，LLM 上下文用
# children → 入 Milvus 索引，检索命中
# children[i].parent_id → 找到对应 parent
# children[i].metadata["parent_content"] → 父块全文，随检索结果返回
```

### 6. Overlap 策略

前后 chunk 重叠 chunk_overlap 个字符。实现方式不是简单滑动窗口——那样会切断句子：

```text
❌ 滑动窗口：
  chunk1: "...消费满6笔即可免"  ← 句子被截断
  chunk2: "笔即可免年费。新客户..."

✓ 递归切分 + overlap：
  切分时保证每个 chunk 在标点处结束
  overlap 内容在末尾截取，拼入下一个 chunk 开头
```

## 技术栈

| 环节 | 工具 |
|------|------|
| 架构 | 策略模式（TextSplitter ABC + SplitPipeline 编排器） |
| 标题切分 | HeadingSplitter / MarkdownSplitter |
| 递归切分 | RecursiveSplitter（中文标点优先级表） |
| 不切分 | NoOpSplitter（表格行 + 图片） |
| 父子块 | ParentChildPipeline（父块先切 → 父内切子 → 关联） |
