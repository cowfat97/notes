# Agent 评估

## 为什么 Agent 评估比模型评估难

LLM 评估只管输入→输出质量，Agent 评估要管输入→**自主决策多步执行**→最终结果。多了三层不确定性：

- **规划质量**：拆解的子任务是否合理？是不是绕路了？
- **工具调用**：工具选对了吗？参数填对了吗？调用次数合理吗？
- **环境交互**：执行中间步骤可能失败或产生副作用，Agent 能否恢复？

## 评估维度

| 维度 | 关注点 | 示例问题 |
|------|--------|----------|
| **任务成功率** | 最终结果是否正确 | 代码能不能跑？机票订对了吗？ |
| **执行效率** | 步骤数、耗时、token 消耗 | 是不是反复试错浪费？ |
| **工具使用准确性** | 工具选择、参数正确性 | `search(query="")` 传空参数？ |
| **鲁棒性** | 异常处理和恢复能力 | API 超时后能不能换方案？ |
| **安全性** | 是否执行危险操作 | 有没有 `rm -rf /`？ |
| **可解释性** | 每一步的决策是否有理有据 | 为什么选了方案 A 而不是 B？ |

## 评估方法

### 人工评估

人工逐条 review Agent 的执行轨迹，打分：

```
任务：帮我在 GitHub 上创建 issue
轨迹：
  1. search("GitHub API create issue")          ← 选了搜索，合理
  2. click("github.com/new")                     ← 选了浏览器操作，也行
  3. fill("title", "bug: ...")                   ← 参数正确
  4. click("Submit")                             ← 操作正确
  5. extract("issue url")                        ← 返回结果
评分：工具选择 4/5，参数准确性 5/5，效率 3/5（步骤多了）
```text

**优点**：最准。**缺点**：贵、慢、不规模化。

### LLM-as-Judge

用另一个更强的 LLM 来做裁判，自动评分：

```text
Prompt:
你是 Agent 评估器，请根据以下标准评分（1~5）：

任务：在 GitHub 上创建一个 issue，内容为"修复登录按钮"
Agent 执行轨迹：[...]
预期结果：[...]

评分维度：
  - 任务完成度：是否达成了目标？
  - 工具选择合理性：每一步的工具选择是否恰当？
  - 参数准确性：工具调用的参数是否正确？
```

**优点**：可规模化，成本可控。**缺点**：LLM 裁判有偏见（偏好自己同类的输出），对多步复杂任务的判断不稳定。常用裁判模型：GPT-4、Claude Opus。

### 基准测试（Benchmark）

| 基准 | 任务类型 | 评估指标 | 说明 |
|------|----------|----------|------|
| **SWE-bench** | 修 Bug | resolved rate | 从 GitHub issue 修 bug 并提交 patch |
| **WebArena** | Web 操作 | success rate | 在真实网站完成购物、搜索等任务 |
| **GAIA** | 通用推理 | accuracy | 多模态多步推理，防 LLM shortcut |
| **OSWorld** | 操作系统 | success rate | 操作系统 GUI 操作，如发邮件、编辑文档 |
| **AgentBench** | 多维能力 | 各维度得分 | 中文 Agent 基准，8 个维度包括代码、Web、游戏 |
| **BFCL** | 函数调用 | accuracy | 评测精确的函数调用参数匹配 |
| **τ-bench（tau-bench）** | 工具使用 | pass@1 | 强调对工具返回结果的正确解读 |
| **ToolBench** | 工具调用 | pass rate | 16 个真实 API 环境下的工具使用 |

### 轨迹评估（Trajectory Evaluation）

不只看最终结果对不对，还要看**每一步对不对**：

- **Step-wise accuracy**：每一步的状态→动作是否符合预期
- **Recovery rate**：失败后能否通过重试/换方案恢复
- **Grounding accuracy**：调用的参数是基于环境真实值还是幻觉出来的

## 评估指标

| 指标 | 公式/含义 | 适用场景 |
|------|-----------|----------|
| **Success Rate** | 成功任务数 / 总任务数 | 所有场景 |
| **Pass@k** | k 次尝试中至少成功一次 | 代码生成 |
| **Average Steps** | 成功任务的平均步数 | 评测效率 |
| **Tool Call Accuracy** | 正确工具调用次数 / 总调用次数 | 工具使用 |
| **Token Efficiency** | 完成任务消耗的 token 数 | 成本敏感场景 |
| **Hallucination Rate** | 幻觉操作占总操作的比例 | 可信度 |
| **Abort Rate** | Agent 放弃执行的比例 | 反脆弱性 |

## 评估框架

| 框架 | 特点 |
|------|------|
| **LangSmith** | LangChain 官方，自动录制轨迹 + LLM-as-Judge |
| **Opik（Comet）** | 开源，trace→evaluate 闭环，支持自定义 metric |
| **Braintrust** | 专注于 eval-driven 开发，A/B 对比 |
| **AgentEval**（微软） | 基于 LLM-as-Judge 的 Agent 专用评估 |
| **SWE-agent 自带评测** | 针对代码修复的 pass/fail 自动化 |

## 实践建议

1. **先定评估目标**：Agent 是对话助手还是自动化工具？评估侧重完全不同
2. **分层评估**：单独测工具调用，再测多步规划，最后端到端
3. **多裁判投票**：LLM-as-Judge 用 2~3 个异构模型交叉验证
4. **构建回归集**：每次修改 Agent 后跑固定的 20~50 个测试用例，防退化
5. **记录 bad case**：评估不仅要统计数据，更要积累典型失败模式
