## 技术分类：三个维度

意图识别的技术方案选择，取决于以下三个正交维度：

```text
                    意图识别的技术分类
         ┌──────────────────────────────────┐
         │                                  │
         │   轮数        类别        时效    │
         │  ┌─────┐   ┌──────┐   ┌──────┐  │
         │  │单轮 │   │单标签│   │实时  │  │
         │  │多轮 │   │多标签│   │离线  │  │
         │  └─────┘   │闭集  │   └──────┘  │
         │            │开集  │              │
         │            └──────┘              │
         └──────────────────────────────────┘
```

### 1. 轮数

| 类型 | 特征 | 技术差异 |
| --- | --- | --- |
| 单轮 | 只看当前输入，不依赖历史 | 直接分类 |
| 多轮 | 依赖对话历史补全上下文 | 意图识别 + 查询改写，或历史拼入 prompt |

多轮的本质不是"更复杂"，是**输入不完整**——"后天呢"这类省略句，单轮没法分类。

### 2. 类别

两个正交的子维度：

| 子维度 | 两种形态 | 关键差异 |
| --- | --- | --- |
| 标签数 | 单标签 / 多标签 | 输出层是 softmax 还是 sigmoid+threshold |
| 集合边界 | 闭集 / 开集 | 是否接受"都不属于" |

四种组合：

| 标签数 | 闭集 | 开集 |
| --- | --- | --- |
| **单标签** | BERT softmax，N 个固定意图 | softmax + out_of_scope 标签 + 置信度兜底 |
| **多标签** | sigmoid，允许多个意图同时命中 | LLM 结构化输出，`["order","weather"]` 或 `["out_of_scope"]` |

#### 闭集 vs 开集

- **闭集（Closed Set）**：训练时所有类别已确定，模型输出必须落在预设标签内。softmax 的竞争性特性导致即使输入不相关也会强行归类。
- **开集（Open Set）**：模型需要能说"这不是我认识的任何一类"。实现方式：
  - `out_of_scope` 标签兜底
  - 置信度阈值：prob < 0.5 → out_of_scope，0.5~0.9 → 追问，> 0.9 且 out_of_scope → 真不归管

out_of_scope 下游三种处理：
1. 直接拒绝，返回引导语
2. 二次确认，缩小范围
3. 转人工

### 3. 时效

| 类型 | 延迟容忍 | 方案选择 |
| --- | --- | --- |
| 实时 | <100ms | BERT 微调，本地推理 |
| 离线 | 秒～分钟级 | LLM API，批量处理 |

## 方案对比：BERT 微调 vs LLM Prompt

| 维度 | BERT 微调 | LLM Prompt |
| --- | --- | --- |
| 方案 | [CLS] → 线性变换 → softmax | Few-shot + 结构化 JSON 输出 |
| 延迟 | <10ms | 500ms~2s |
| 成本 | 训练一次，推理几乎免费 | 每次调用付费 |
| 灵活度 | 新增意图需重新训练 | 改 prompt 即可，分钟级上线 |
| 多标签 | 需改输出层为 sigmoid | 原生支持 |
| 开集 | 需专门设计 OOS 机制 | 天然支持"不属于任何一类" |
| 准确率 | 固定类别上更高 | 通用能力强，边缘 case 好 |
| 适用场景 | 标签固定、低延迟、高吞吐 | 标签常变、需要灵活性、低频调用 |

选择原则：**标签固定 + 低延迟 → BERT；标签常变 + 灵活性 → LLM。**

## 两层意图识别架构

一层只做粗粒度二分类，细粒度交给下游。

### 审批系统

```text
                        用户输入
                           │
                           ▼
            第一层：BERT 二分类（2000条，93%）
                 办理 vs 查询
                           │
              ┌────────────┴────────────┐
              ▼                         ▼
           办理                       查询
              │                         │
              ▼                         ▼
      LLM AgentRouter           第二层：BERT 二分类（96%）
            │                   ├── 政策（办卡前咨询）→ RAG
     ┌──────┼──────┐            └── 进度（办卡后查询）→ MCP
     ▼      ▼      ▼
   外数   审批   决策
```

| 层 | 模型 | 分类 | 场景 | 下游 |
| --- | --- | --- | --- | --- |
| 第一层 | BERT 二分类 93% | 办理 / 查询 | — | 分岔到两条完全不同的链路 |
| 第二层 | BERT 二分类 96% | 政策 / 进度 | 查询侧 | 政策走 RAG，进度走 MCP |

无效路由降低 40%+。之前没有第一层，查询请求被当成办理请求丢给 AgentRouter，或者反过来——一刀切开后各走各路。

第二层只在查询侧生效。办卡前咨询（"年费多少"）走 RAG 知识库，办卡后查询（"我的申请到哪了"）走 MCP 查数据库。办理侧不分类——LLM AgentRouter 通过槽位提取和工作流编排确定具体子类（外数/审批/决策）。

### 客服系统

```text
                        用户输入
                           │
                           ▼
            第一层：BERT 二分类
                 办理 vs 查询
                           │
              ┌────────────┴────────────┐
              ▼                         ▼
           办理                       查询
       办卡咨询                         │
                                       ▼
                              第二层：BERT 分类
                                ├── 账单 → RAG
                                ├── 规则 → RAG
                                └── 积分 → RAG
```

查询侧三类走同一个 RAG——检索路径不同，但都是检索+生成的 pipeline，不需要 Agent。

### 为什么是两层

第一层切粗粒度（办 vs 查），分岔到两条完全不同的后端链路。第一层的错误代价高——走错链路意味着整个系统做错事。

第二层切细粒度，在同一链路内选检索路径。第二层的错误代价低——查错了 RAG 路径，召回的文档质量差一些，但不会完全答非所问。

一层承载路由正确性，二层承载检索精度。一个 BERT 没法同时优化两个目标。

### 对照

| | 审批系统 | 客服系统 | SmartVoyage |
| --- | --- | --- | --- |
| 第一层 | BERT 办/查 2000条 93% | BERT 办/查 | — |
| 第二层 | BERT 政策/进度 96% | BERT 账单/规则/积分 | — |
| 轮数 | 单轮 | 单轮 | 多轮（意图+改写） |
| 开集 | 闭集 | 闭集 | 开集（out_of_scope） |
| 方案 | BERT 微调 | BERT 微调 | LLM + 结构化 JSON |
