# vLLM 长上下文性能实验

## 实验目的

验证上下文变长后，vLLM 的延迟、显存、KV Cache 和并发能力如何变化，并确定 4096 或 8192 哪个更适合作为默认 `max-model-len`。

本实验不以“请求没有报错”为通过，而同时检查：

- 输入是否真的达到目标 Token 长度
- 请求在目标长度下能否稳定完成
- 延迟、KV Cache 和并发容量如何变化
- 超过上限时能否返回明确错误

## 核心原则

`--max-model-len` 是服务端允许的最大序列长度，不代表每个请求都会占满全部 KV Cache。提高该值的价值取决于真实业务是否需要长对话。

不能用字符数代替 Token 数。测试数据必须经过 Qwen tokenizer 计数，并保存实际 `prompt_tokens`。

## 前置条件

- 先完成 4096 配置测试
- 测试 8192 前重启 vLLM，并确认 `/v1/models` 返回新的 `max_model_len`
- 固定模型、温度、输出上限和提示模板
- 每个档位预热 3 次
- 每次只改变上下文长度或目标事实位置中的一个变量

## 服务配置

### 4096 组

```bash
VLLM_USE_V2_MODEL_RUNNER=0 \
VLLM_USE_FLASHINFER_SAMPLER=0 \
vllm serve Qwen/Qwen3-4B \
  --host 127.0.0.1 \
  --port 8000 \
  --max-model-len 4096 \
  --gpu-memory-utilization 0.90
```

### 8192 组

```bash
VLLM_USE_V2_MODEL_RUNNER=0 \
VLLM_USE_FLASHINFER_SAMPLER=0 \
vllm serve Qwen/Qwen3-4B \
  --host 127.0.0.1 \
  --port 8000 \
  --max-model-len 8192 \
  --gpu-memory-utilization 0.90
```

## 测试数据

构造自然语言材料，通过增减段落控制输入 Token 数。各档位使用相同主题和相近语言分布，提示模型只输出固定短答案，减少生成内容差异对性能结果的干扰。

事实召回、位置效应和上下文组织策略移至 `Agent/3.1_上下文构建与语言实验.md`。

这里的目标长度是输入 Token，必须给系统提示、材料、问题和输出预留空间。若使用 `max_tokens=128`，请求总长度不能超过服务上限。

## 边界测试

额外发送两类请求：

1. 总 Token 刚好低于服务上限。
2. 总 Token 明确超过服务上限。

超限请求应快速返回 4xx 和清晰错误，不得导致 EngineCore 崩溃或长时间占用 GPU。

## 指标

| 指标 | 含义 |
| --- | --- |
| 实际 prompt tokens | 服务返回的 `usage.prompt_tokens` |
| 首 Token 延迟 | 流式请求收到首个非空文本片段的时间 |
| 总延迟 | 请求到完整响应的时间 |
| 峰值显存 | 请求期间最高 GPU 显存占用 |
| KV Cache 使用率 | vLLM 指标或日志中的缓存占用 |
| 最大并发估计 | 启动日志给出的 maximum concurrency |

## 避免无效实验

- 不要只重复同一个词凑长度，分布与真实文本差异太大。
- 固定输出任务和输出上限，避免生成内容差异污染性能结果。
- 不要同时修改模型、上下文、温度和提示词。
- 不要因为显存允许 8192，就默认业务必须使用 8192。

## 判定标准

默认上下文上限应满足：

- 所有目标长度请求成功完成
- 超限请求能明确失败，服务进程保持健康
- 延迟和并发容量仍满足业务要求

如果真实业务对话通常低于 3000 Token，且 8192 没有带来实际功能收益，则默认保留 4096。

## 实验产出

实验结束只给出：

1. 推荐的默认 `max-model-len`。
2. 可可靠召回的实测上下文长度。
3. 长上下文对延迟、显存和并发的代价。
