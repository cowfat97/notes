# vLLM 改造实验

## 实验目的

将当前 `Transformers + Outlines` 与 FastAPI 同进程的本地推理方式，改造为业务服务与 vLLM 推理服务分离的架构。

本实验重点回答：

- vLLM 能否在当前 RTX 5060 Ti 16GB 设备上稳定运行 Qwen3，并从 1.7B 逐级升级到 4B 或 8B-AWQ
- 业务层改为 HTTP 调用后，ReAct 循环、记忆和 FastAPI 接口能否保持现有行为
- vLLM JSON Schema 结构化输出能否替代 Outlines 本地约束解码
- 与 CPU 裸跑基线相比，首 Token 延迟、总延迟和并发吞吐改善多少
- vLLM 不可用时，业务层能否给出明确错误，而不是在启动阶段卡死

## vLLM JSON Schema 的替代边界与兜底

结论：vLLM JSON Schema 可以承担主要的语法约束解码，但不能单独替代整套输出控制。可以移除业务进程内与 Transformers 紧耦合的 Outlines generator，但必须保留状态机边界、Pydantic 校验、有限重试和确定性降级。

当前链路：

```text
Transformers 生成
  → Outlines 根据 ActionOutput 约束每个 Token
  → 生成 JSON
  → Pydantic 解析为 ActionOutput
```

vLLM 改造后：

```text
业务层把 ActionOutput JSON Schema 发给 vLLM
  → vLLM 在服务端执行结构化约束解码
  → OpenAI 兼容接口返回 JSON 文本
  → Pydantic 再做一次独立校验
```

两者的职责映射：

| 当前实现 | vLLM 改造后 | 是否保留 |
| --- | --- | --- |
| `outlines.from_transformers(model, tokenizer)` | vLLM 独立推理服务 | 不保留 |
| `output_type=ActionOutput` | `response_format.type=json_schema` | 改为 HTTP 请求参数 |
| `ActionOutput.model_json_schema()` | 发给 vLLM 的 Schema | 保留 |
| `ActionOutput.model_validate_json()` | 校验 vLLM 响应 | 必须保留 |
| `fallback_reply()` | 最后的确定性降级 | 保留，但不直接吞掉上游错误 |

### 分层输出防线

改造后的完整链路不能只有一个 `response_format`，而应设计为五层防线：

```text
第 1 层：ReAct 流程状态机
  限制当前允许的行动、工具调用次数和最大循环步数
            ↓
第 2 层：vLLM JSON Schema 约束解码
  在 Token 生成阶段限制 JSON 形状、字段类型和 action 枚举
            ↓
第 3 层：Pydantic 二次校验
  不信任 HTTP 返回文本，再次检查完整性和字段契约
            ↓
第 4 层：有限重试
  只对可恢复错误重试，每次重试必须有明确的修正信息
            ↓
第 5 层：确定性降级与熔断
  达到上限后停止生成，返回可诊断错误或安全回复
```

### ReAct 状态机仍然必须保留

JSON Schema 只能限制 `action` 必须是 `answer` 或 `memory_search`，不能保证模型在当前步骤选对行动。

例如，已经执行过一次 `memory_search` 后，JSON Schema 仍然允许模型再次返回合法的：

```json
{
  "thought": "继续检索",
  "action": "memory_search",
  "argument": "羽毛球"
}
```

该 JSON 在语法上完全合法，但在当前 ReAct 状态下已经违反“检索最多一次”的业务规则。因此必须继续使用：

- `max_steps` 限制总循环步数
- `max_search` 限制工具调用次数
- 显式的当前状态和允许行动集合
- Observation 中的下一步约束
- 程序端的行动白名单和转移校验

进一步可以按状态生成不同 Schema：

```text
初始状态：action 允许 answer | memory_search
检索后状态：action 只允许 answer
结束状态：不再调用模型
```

这比只在 Prompt 中写“不要再检索”更强，因为不合法行动在解码阶段就无法被生成。

### 重试机制

重试应该有上限、分类和修正信息，不能对同一请求无限重放。

| 错误 | 是否重试 | 处理 |
| --- | --- | --- |
| 连接瞬断、502、503 | 是 | 短退避后重试 |
| 请求超时 | 有条件 | 只重试一次，防止模型在后台重复执行 |
| 空响应 | 是 | 注入“上次输出为空”后重试 |
| JSON 截断 | 是 | 缩短 Prompt 或增加 `max_tokens` 后重试 |
| Pydantic 校验失败 | 是 | 把具体校验错误作为修正信息 |
| 业务状态不允许该 action | 是 | 使用当前状态的收紧 Schema 重试 |
| 400 参数或 Schema 错误 | 否 | 立即失败，修正程序配置 |
| 模型不存在 | 否 | 立即失败，检查 `VLLM_MODEL` |

建议限制：

```text
单次模型生成最多重试 2 次
单轮 ReAct 最多 3 步
memory_search 最多 1 次
连续上游失败达阈值后短时熔断
```

每次重试都要记录 `request_id`、尝试次数、错误分类和耗时，但不把凭据和完整私密对话写入日志。

### 最终降级

重试耗尽后不能把非法 JSON 直接当作正常回答返回。应根据失败类型选择：

- 上游不可用：返回明确的服务暂不可用错误
- 结构持续非法：返回固定安全文案，并标记结构生成失败
- 行动转移非法：拒绝执行工具，强制进入 `answer` 或结束状态
- 已产生可校验的 `argument`：只有在明确的降级契约下才能提取，不应默默吞掉错误

本实验不在 `vllm` 分支内保留 Outlines 或 Transformers 回退实现。Outlines 需要控制本地 logits，无法对已经由 HTTP 返回的文本重做 Token 约束；同一分支保留两套后端还会引入依赖、启动和错误语义混乱。

分支职责固定为：

```text
main：保存 Transformers + Outlines 裸跑基线
vllm：只实现 vLLM HTTP 推理路径
```

如果 vLLM 改造失败，通过 Git 切回 `main` 进行对照或回退，而不是在单个请求中自动加载 Transformers 模型。

当前 Schema：

```python
class ActionOutput(BaseModel):
    thought: str
    action: Literal["answer", "memory_search"]
    argument: str
```

该结构只包含固定字段、字符串和枚举，没有递归对象、动态键或复杂条件，属于适合 vLLM JSON Schema 结构化输出的场景。

预期请求格式：

```python
response = client.chat.completions.create(
    model=model_name,
    messages=turns,
    max_tokens=512,
    temperature=0,
    response_format={
        "type": "json_schema",
        "json_schema": {
            "name": "action_output",
            "schema": ActionOutput.model_json_schema(),
        },
    },
)

model_output = response.choices[0].message.content
output = ActionOutput.model_validate_json(model_output)
```

需要单独验证的边界：

- Qwen3 thinking 内容是否会进入 JSON 正文并破坏 Schema
- 结构化输出首次编译 Schema 带来的额外延迟
- `max_tokens` 过小时输出被截断的处理
- vLLM 版本变化对 OpenAI `response_format` 协议的影响
- HTTP 超时、断连和空响应不属于 Schema 能解决的问题

验收标准：使用固定 20 条输入，每条重复 5 次，共100 次生成；要求 JSON 语法合法率、Pydantic 校验通过率和 `action` 枚举合法率全部达到 100%。另外注入断连、超时、空响应、截断 JSON 和非法状态转移，验证重试上限、降级结果和 memory 不被污染。`vllm` 分支实现时直接移除 Outlines 与 Transformers 运行依赖，但仍保留状态机、Pydantic 校验、有限重试和熔断逻辑。

## 模型升级路线

`Qwen/Qwen3-1.7B` 只是跑通 vLLM 链路的起点，不是最终上限。当前 RTX 5060 Ti 具有 16GB 显存，实验按以下三档逐级验证：

| 阶段 | 模型 | 定位 | 预期 |
| --- | --- | --- | --- |
| A | `Qwen/Qwen3-1.7B` | 链路验证 | 显存余量大，快速确认 WSL、CUDA、vLLM 和 JSON Schema |
| B | `Qwen/Qwen3-4B` | 稳定使用 | BF16 下仍能给 KV Cache 和并发留出空间 |
| C | `Qwen/Qwen3-8B-AWQ` | 能力优先 | 4-bit AWQ 明显降低权重显存，适合 16GB 单卡重点测试 |

不建议把 `Qwen/Qwen3-8B` BF16 作为首选。8B 权重的理论占用已接近 16GB，还没计入 KV Cache、CUDA Context 和 vLLM 运行开销，可能需要显著缩短上下文或降低并发。

模型不在业务代码中写死，通过 `VLLM_MODEL` 切换。每个模型都必须重新运行功能、结构合法率和性能实验，不能只验证“能加载”。

## 目标架构

```text
Windows 业务进程
  FastAPI :8000
  ReAct 循环
  Session Memory
  Pydantic 校验
          |
          | OpenAI 兼容 HTTP API
          v
WSL2/Linux 推理进程
  vLLM :8001
  Qwen/Qwen3-1.7B
  CUDA / RTX 5060 Ti
```

端口分工：

| 端口 | 职责 |
| --- | --- |
| `8000` | 现有 FastAPI 业务接口 |
| `8001` | vLLM OpenAI 兼容推理接口 |

Windows 的 `.venv` 继续用于业务层，vLLM 必须使用 WSL2/Linux 中的独立虚拟环境。两个环境不共享 Python 包和 PyTorch。

## 实验边界

本轮处理：

- 单机、单张 NVIDIA GPU
- Qwen3-1.7B、Qwen3-4B 和 Qwen3-8B-AWQ 三档单模型对比
- vLLM OpenAI Chat Completions 接口
- JSON Schema 结构化输出
- 现有 ReAct `answer` / `memory_search` 行动
- 现有 `POST /chat` 接口

本轮不处理：

- 多机或多 GPU 并行
- 模型量化对比
- LoRA 动态加载
- 长期记忆和向量数据库
- 公网暴露、鉴权和反向代理
- 自动扩缩容

## 核心改造原则

### 业务层不加载模型

`qwen_chat.py` 不再创建 `AutoModelForCausalLM`、`AutoTokenizer` 和 Outlines generator。它只保留：

- ReAct 循环
- 行动解析
- 记忆读写
- vLLM 客户端调用

### 推理层与业务层解耦

不要把 vLLM 的启动命令放进 `controller.py`。两个进程独立启停：

```text
先启动 vLLM
  → 验证 /v1/models
  → 再启动业务 FastAPI
  → 验证 /chat
```

### 配置不写死

至少支持以下环境变量：

| 变量 | 默认值 |
| --- | --- |
| `VLLM_BASE_URL` | `http://127.0.0.1:8001/v1` |
| `VLLM_MODEL` | 实验阶段指定，起始值为 `Qwen/Qwen3-1.7B` |
| `VLLM_API_KEY` | `EMPTY` |
| `VLLM_TIMEOUT` | `300` |

### 保留输出契约

现有 `ActionOutput` 结构不变：

```json
{
  "thought": "简短说明",
  "action": "answer 或 memory_search",
  "argument": "回复或检索关键词"
}
```

原来由 Outlines 在 Transformers 生成过程中执行约束；改造后，将 `ActionOutput.model_json_schema()` 作为 `response_format` 发给 vLLM。

Pydantic 二次校验必须保留，不能因为 vLLM 已做约束就删除 `parse_action()` 的校验。

## 分阶段实验

### A：保留当前 CPU 裸跑基线

- 固定现有代码和依赖
- 运行固定测试集
- 记录单请求和并发请求数据
- 作为功能与性能对照组

### B：只启动 vLLM

目标是先验证推理服务，不修改业务代码。

预期启动参数：

```bash
vllm serve Qwen/Qwen3-1.7B \
  --host 0.0.0.0 \
  --port 8001 \
  --dtype auto \
  --max-model-len 8192 \
  --gpu-memory-utilization 0.80
```

观察点：

- WSL 内 `nvidia-smi` 是否能看到 RTX 5060 Ti
- 模型能否完整加载
- 峰值显存占用
- `/v1/models` 是否返回 `Qwen/Qwen3-1.7B`
- `/v1/chat/completions` 是否能生成中文回复
- Windows 是否能通过 `127.0.0.1:8001` 访问 WSL 服务

1.7B 链路通过后，使用同一套参数分别替换模型名：

```bash
# 稳定档
vllm serve Qwen/Qwen3-4B \
  --host 0.0.0.0 \
  --port 8001 \
  --dtype auto \
  --max-model-len 8192 \
  --gpu-memory-utilization 0.80

# 16GB 单卡能力档
vllm serve Qwen/Qwen3-8B-AWQ \
  --host 0.0.0.0 \
  --port 8001 \
  --max-model-len 8192 \
  --gpu-memory-utilization 0.85
```

AWQ 模型的量化方式通常可由 vLLM 根据模型配置自动识别。首次测试不同时开启 reasoning parser，先验证现有 ReAct JSON 协议；如果后续研究 Qwen thinking 模式，再单独增加实验组。

### C：最小客户端替换

只替换模型生成边界：

```text
generator(Chat(turns), output_type=ActionOutput)
```

改为：

```text
OpenAI client
  → base_url=http://127.0.0.1:8001/v1
  → messages=turns
  → response_format=ActionOutput JSON Schema
  → 取 choices[0].message.content
```

除此之外，ReAct 循环、`execute()`、`parse_action()` 和 memory 全部保持不变。

### D：错误处理

主动模拟：

- vLLM 未启动
- vLLM 请求超时
- vLLM 返回空内容
- 模型名与已服务模型不匹配
- JSON Schema 请求被拒绝
- 返回内容无法通过 Pydantic 校验

业务接口应该区分上游推理错误与自身业务错误，日志中记录错误类型和耗时，但不记录 API Key。

### E：并发对比

分别测试：

- 串行 10 次
- 并发 2 路
- 并发 4 路
- 并发 8 路

每组使用同一批提示词。不能只对比某一次最快请求，应记录平均值、P50、P95 和总吞吐。

## 功能测试用例

### 1. 普通回答

```text
用户：请用一句话介绍大语言模型。
```

期望：

- HTTP 200
- `action=answer`
- `argument` 是非空中文文本
- 对外响应仍为 `reply/count/chars`

### 2. 记忆检索

```text
第一轮：我喜欢羽毛球。
第二轮：我之前说过喜欢什么运动？
```

期望：

- 第二轮先生成 `memory_search`
- Observation 写回记忆
- 下一步生成 `answer`
- 最终回答包含“羽毛球”

### 3. JSON Schema 稳定性

固定 20 条输入，每条重复 5 次，共 100 次生成。

期望：

- 100% 可被 `ActionOutput.model_validate_json()` 解析
- `action` 只出现 `answer` 或 `memory_search`
- 不出现 JSON 外的标题、Markdown 或解释

### 4. vLLM 未启动

停止 8001 端口后调用 `/chat`。

期望：

- 快速失败，不无限等待
- 日志明确显示 vLLM 连接失败
- 已有 session memory 不被错误响应污染

### 5. vLLM 恢复

重新启动 vLLM，不重启业务 FastAPI，再次调用 `/chat`。

期望：业务进程自动恢复调用，不需要重新 import 模型或重建客户端。

## 性能指标

| 指标 | 含义 |
| --- | --- |
| 冷启动耗时 | 启动 vLLM 到 `/v1/models` 可用 |
| 首 Token 延迟 | 提交请求到收到第一个 Token |
| 总延迟 | 提交请求到完整响应 |
| 输出速度 | 每秒生成 Token 数 |
| 请求吞吐 | 单位时间完成请求数 |
| P50 / P95 | 中位和尾部延迟 |
| GPU 显存 | 空闲、单请求和并发时的显存占用 |
| GPU 利用率 | 生成阶段的 GPU 忙碌程度 |
| 结构合法率 | Pydantic 校验通过数 / 生成总数 |
| 功能一致率 | 与基线行为一致的用例数 / 总用例数 |

## 控制变量

对比 CPU 裸跑与 vLLM 时，保持：

- 模型名称和模型权重一致
- System Prompt 一致
- 输入 messages 一致
- `max_tokens=512`
- `temperature=0`
- 相同的测试顺序与重复次数
- 预热规则一致

Qwen 的 chat template 和 `generation_config.json` 可能改变采样行为，实验记录中必须保存 vLLM 启动命令和实际参数，不能只写“使用默认值”。

## 验收条件

改造完成必须同时满足：

1. vLLM 使用 RTX 5060 Ti 跑通 `Qwen/Qwen3-1.7B`，并至少完成 `Qwen/Qwen3-4B` 或 `Qwen/Qwen3-8B-AWQ` 一档升级验证。
2. Windows 业务环境不再加载 Transformers 模型权重。
3. `POST /chat` 请求和响应契约保持不变。
4. `answer` 和 `memory_search` 两条 ReAct 路径都通过。
5. 结构化输出合法率达到 100%。
6. vLLM 断开时能在超时范围内返回可诊断错误。
7. vLLM 恢复后，业务服务无需重启即可继续调用。
8. 固定测试集的总延迟和吞吐数据完整可复现。

## 回退策略

基线不保留在 `vllm` 分支的运行代码中，而由 `main` 分支完整保存。出现以下任一情况时，暂停 `vllm` 分支的实施，切回 `main` 复现基线并定位差异：

- vLLM 无法识别 RTX 5060 Ti
- Qwen3-1.7B 在目标 vLLM 版本上无法加载
- JSON Schema 与 Qwen3 thinking 输出冲突
- ReAct 行动选择与基线明显不一致
- Windows 到 WSL 的本地网络连接不稳定
- 单请求延迟或并发吞吐没有达到实验目标

不实现：

- `LLM_BACKEND=vllm/transformers` 双后端切换
- vLLM 失败后单请求自动回退 Transformers
- Windows 业务进程临时加载模型权重
- `vllm` 分支继续依赖 Outlines

## 建议实施顺序

1. 保存 CPU 裸跑基线数据。
2. 安装 WSL2 并验证 GPU 透传。
3. 在 WSL 建立独立 `llm-vllm` 环境。
4. 用 Qwen3-1.7B 启动 vLLM 8001 端口，先做原生 API 测试。
5. 增加最小 vLLM 客户端，不立即删除原生 Transformers 路径。
6. 使用 JSON Schema 复现 `ActionOutput` 约束。
7. 跑通普通回答和记忆检索。
8. 增加断连、超时、空回复和非法 JSON 测试。
9. 运行串行与并发性能对比。
10. 依次替换为 Qwen3-4B 和 Qwen3-8B-AWQ，复用完整测试集。
11. 根据质量、延迟、显存和并发结果确定默认模型。
12. 数据达标后，再清理 Windows 业务环境中不再需要的模型推理依赖。
