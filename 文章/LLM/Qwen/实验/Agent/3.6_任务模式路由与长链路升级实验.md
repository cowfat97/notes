# Agent 任务模式路由与长链路升级实验

## 实验背景

当前 `vllm_chat.py` 对所有请求使用同一条 ReAct 链路，并通过：

```python
for step in range(1, 6):
```

把一次用户请求限制为最多 5 次行动。该限制能够防止无限循环，但无法区分：

- 一次回答即可完成的普通任务；
- 需要持续执行和完成审计的单一长目标；
- 包含多个可独立验收交付物的复杂任务。

本实验设计三种任务模式：

```text
normal   普通短任务
goal     单一长目标
mission  多个独立交付任务
```

实验重点不是立即实现完整 Mission 系统，而是验证模式判断应该使用纯规则、纯模型还是混合路由，并验证运行中何时允许模式升级。

## 实验目标

回答以下问题：

1. 关键词或程序规则能否准确区分三种任务模式？
2. 模型结构化分类是否比规则更准确、是否稳定？
3. “规则优先、模型补充、程序校验”是否是更合理的路由方案？
4. 普通模式在 5 步窗口耗尽前，能否可靠升级为 Goal？
5. Goal 是否应该自动升级为 Mission？
6. 模式路由增加的模型调用和 Token 成本是否值得？

## 模式定义

### Normal

满足以下特征：

- 一次回答或少量明确操作即可完成；
- 不需要跨执行窗口保存进度；
- 没有持续执行要求；
- 不包含多个独立交付物。

示例：

```text
解释什么是 vLLM。
检查 8001 端口是否可访问。
读取 requirements.txt。
把模型名改成 Qwen3-4B。
```

### Goal

满足以下特征：

- 只有一个主要目标；
- 需要连续探索、执行、验证或重试；
- 中间步骤相互依赖；
- 可能跨多个 5 步执行窗口；
- 完成前需要检查证据。

示例：

```text
排查并修复 vLLM 启动失败，直到接口验证成功。
完成一次长上下文实验并得出结论。
分析依赖冲突并解决所有相关错误。
```

### Mission

必须同时具备：

- 至少两个相对独立的交付物；
- 每个交付物有独立验收标准；
- 一个子任务失败时，其他子任务仍可推进；
- 子任务上下文隔离具有实际收益。

示例：

```text
完成 vLLM 系统改造：
1. 推理服务接入；
2. Web 接口改造；
3. 并发压测；
4. 部署文档。
```

“步骤很多”不等于 Mission。排查一个复杂 CUDA 错误即使需要 30 步，仍然属于 Goal。

## 路由方案

### A 组：纯关键词规则

通过正则表达式和关键词直接分类：

```text
解释 / 什么是 / 查询一次       → normal
直到完成 / 不要停止 / 修复并验证 → goal
多个模块 / 分别完成 / 批量       → mission
```

优点：速度快、零额外模型 Token、结果确定。

风险：

- “这个函数完成了什么”可能因“完成”被误判为 Goal；
- 编号列表可能只是顺序步骤，并非独立交付物；
- 难以理解否定、疑问和隐含任务结构。

### B 组：纯模型判断

每个请求先调用模型，要求返回结构化分类：

```json
{
  "mode": "goal",
  "confidence": 0.86,
  "primary_goal": "修复 vLLM 服务并验证接口",
  "deliverables": [
    {
      "name": "可用的 vLLM 服务",
      "independent": false,
      "acceptance_criteria": [
        "/v1/models 返回 200",
        "聊天接口成功生成回答"
      ]
    }
  ],
  "requires_persistence": true,
  "requires_completion_audit": true,
  "execution_path_known": false,
  "reason_codes": [
    "MULTI_TURN_EXECUTION",
    "REQUIRES_VERIFICATION"
  ]
}
```

优点：能够理解自然语言和任务结构。

风险：增加一次模型调用；相同输入可能波动；模型可能给出自相矛盾的字段。

### C 组：规则优先 + 模型补充 + 程序校验

处理流程：

```text
显式模式命令
→ 运行时硬状态
→ 强语义规则
→ 简单结构检测
→ 模糊任务交给模型分类
→ 程序校验和降级
```

路由伪代码：

```python
def choose_mode(text, runtime=None):
    explicit = parse_explicit_mode(text)
    if explicit:
        return explicit

    if runtime and should_upgrade_runtime(runtime):
        return "goal"

    hard_result = match_strong_rules(text)
    if hard_result:
        return hard_result

    features = analyze_request_structure(text)
    if features.simple_single_action:
        return "normal"

    classification = model_classify(text, features)
    return validate_and_normalize(classification)
```

## 硬规则范围

硬规则不是普通的单关键词匹配，只处理高置信信号。

### 显式命令

```text
/normal
/goal
/mission
```

用户显式指定优先级最高。

### Goal 强语义短语

```text
直到成功
直到完成
持续检查直到……
修复并验证
完成后再结束
```

必须匹配完整短语，并排除引用、解释和否定语境。

### 疑问和否定排除

以下请求不能因包含模式关键词而启动对应模式：

```text
Goal 模式是什么？
解释“直到完成”的含义。
不要使用 Goal 模式。
为什么这个任务不需要 Mission？
```

### Mission 候选结构

程序可以检测编号列表、标题和多个动词对象，但只标记为 `mission_candidate`，不能直接确认 Mission。

模型需要进一步判断这些项目是：

```text
一个目标的顺序步骤
还是
多个可独立验收的交付物
```

## 模型分类 Schema

分类模型必须输出合法 JSON：

```json
{
  "mode": "normal | goal | mission",
  "confidence": 0.0,
  "primary_goal": "string",
  "deliverables": [
    {
      "name": "string",
      "independent": true,
      "acceptance_criteria": ["string"]
    }
  ],
  "requires_persistence": false,
  "requires_completion_audit": false,
  "execution_path_known": true,
  "reason_codes": ["string"]
}
```

固定 `reason_codes`：

```text
SIMPLE_QA
SINGLE_KNOWN_ACTION
MULTI_TURN_EXECUTION
UNCERTAIN_EXECUTION_PATH
REQUIRES_VERIFICATION
REQUIRES_PERSISTENCE
MULTIPLE_DELIVERABLES
INDEPENDENT_SUBTASKS
CONTEXT_ISOLATION_BENEFICIAL
```

## 程序校验规则

模型返回结果不能直接控制执行器。

### Mission 校验

```python
if result.mode == "mission":
    valid = (
        len(result.deliverables) >= 2
        and all(d.acceptance_criteria for d in result.deliverables)
        and sum(d.independent for d in result.deliverables) >= 2
    )
    if not valid:
        result.mode = "goal"
```

### Normal 校验

```python
if result.mode == "normal" and (
    result.requires_persistence
    or result.requires_completion_audit
):
    result.mode = "goal"
```

### 低置信度校验

```python
if result.confidence < 0.60:
    result.mode = "goal"
```

模糊任务默认归入 Goal，而不是 Normal 或 Mission：Normal 可能过早停止，Mission 的协调成本又过高。

## 长链路运行时升级

### Normal → Goal

当前代码每个请求最多 5 个行动。升级判断必须在第 4 步或更早执行，为 checkpoint 留出空间。

触发条件：

```python
should_upgrade = (
    mode == "normal"
    and not completed
    and (
        actions_used >= 4
        or checkpoint_required
        or completion_verification_pending
        or remaining_work_count >= 2
    )
)
```

不能仅因为达到第 4 步就升级，必须同时存在“任务未完成”的证据。

升级时保存：

```json
{
  "goal": "string",
  "completed": [],
  "pending": [],
  "facts": [],
  "artifacts": [],
  "failures": [],
  "next_action": "string"
}
```

然后用 Goal + checkpoint 重建短上下文，开始新的执行窗口。

### Goal → Mission

第一版不自动升级。模型只能提出：

```json
{
  "proposal": "upgrade_to_mission",
  "deliverables": []
}
```

程序校验独立交付物和验收标准后，由用户确认是否升级。

原因：Goal → Mission 会改变任务结构、执行隔离和状态存储，属于比 Normal → Goal 更大的行为变化。

### Normal 示例

```text

```

### Goal 示例


```text

```


## 实验阶段

### 阶段一：离线路由准确率

不执行真实工具，只对 60 条请求分类。

每种方案重复：

- A 组规则分类 1 次，因为结果确定；
- B 组纯模型分类 5 次；
- C 组混合分类 5 次。

模型组分别测试：

```text
temperature=0
temperature=0.3
```

记录每次分类、置信度、reason codes、Token 和延迟。

### 阶段二：运行时升级

准备 15 个最初看似简单、执行后会暴露复杂性的任务：

```text
检查服务状态
→ 服务未启动
→ 启动失败
→ 需要检查日志和CUDA
```

验证：

- 是否在第 5 步耗尽前发现未完成；
- 是否成功生成 checkpoint；
- 是否从 Normal 切换到 Goal；
- 是否能从 checkpoint 继续而不重复已完成操作；
- 是否最终完成或明确阻塞。

### 阶段三：Goal → Mission 提议

准备 10 个 Goal，在执行中逐渐暴露多个子任务。

评估模型是否能够正确提出 Mission 候选，同时统计错误拆分率。第一版只记录提议，不实际自动升级。

## 对照组

| 组别 | 判断方法 | 运行时升级 |
| --- | --- | --- |
| A | 纯关键词和正则规则 | 固定规则 |
| B | 每次都由模型分类 | 模型建议 |
| C | 规则优先、模型补充、程序校验 | 运行状态硬规则 |
| D | 所有任务固定使用当前 5 步 Normal | 不升级 |

D 组用于测量模式路由是否真的提高长任务完成率，而不只是增加系统复杂度。

## 评估指标

| 指标 | 说明 |
| --- | --- |
| 总准确率 | 模式分类与人工标注一致的比例 |
| Normal 精确率/召回率 | 是否错误把长任务当成短任务 |
| Goal 精确率/召回率 | 是否过度使用 Goal |
| Mission 精确率/召回率 | 是否正确识别独立交付物 |
| 重复运行一致率 | 同一请求多次分类是否一致 |
| 否定误判率 | 否定或元问题是否触发错误模式 |
| 顺序步骤误判率 | 是否把顺序步骤错误当作 Mission |
| 路由 Token | 分类本身消耗的 Token |
| 路由延迟 | 分类增加的请求时间 |
| 升级及时率 | 是否在窗口耗尽前升级 |
| Checkpoint 完整率 | 是否包含继续执行所需状态 |
| 重复行动率 | 升级后是否重复已完成操作 |
| 长任务完成率 | 长链路最终是否完成 |
| 无意义升级率 | 本可短任务完成却升级的比例 |

## 验收标准

推荐 C 组作为默认路由器，需要满足：

1. 三类任务总准确率不低于 90%。
2. Normal 错判导致长任务提前停止的比例不高于 5%。
3. 否定、引用和模式元问题的误触发率不高于 2%。
4. 顺序步骤误判为 Mission 的比例不高于 5%。
5. 相同请求在 `temperature=0` 下分类一致率不低于 98%。
6. Normal → Goal 能在当前 5 步窗口耗尽前完成 checkpoint。
7. 升级后不会重新执行已经确认完成的操作。
8. 相比固定 5 步的 D 组，长任务完成率显著提高。
9. Goal → Mission 第一版只提出建议，不未经确认改变任务执行结构。

2. 哪些任务结构必须交给模型判断？
