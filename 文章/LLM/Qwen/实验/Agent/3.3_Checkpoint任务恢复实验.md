# Agent Checkpoint 任务恢复实验

## 学习定位

本实验研究长链路任务如何拆分、保存进度并从中断处恢复。当前只设计实验，不立即改造 `vllm_chat.py`。

```text
会话记忆：保存“用户和模型聊过什么”
Checkpoint：保存“任务执行到哪里、哪些结果已验证、下一步是什么”
```

## 实验目标

1. 单轮达到行动上限后保存进度，而不是回滚整个任务。
2. Web 服务重启后从最新有效 Checkpoint 恢复。
3. 已完成步骤不重复执行，全局预算不因恢复而归零。
4. 两个请求并发更新时不相互覆盖。
5. 最新 Checkpoint 损坏时回退到上一有效版本。
6. Checkpoint 恢复比重放完整会话使用更少 Token。

## 当前项目基线

- 模型：`Qwen/Qwen3-4B`
- API：`http://127.0.0.1:8000/v1`
- 单轮 ReAct 上限：5 步
- 当前行为：超过 5 步时抛出异常并回滚本轮会话记忆

## 实验任务

设计一个确定性的 10 步任务：创建计划、依次计算 8 个表达式、生成汇总报告。每个计算步骤必须经过计算器和独立核验，结果可重复验证，不依赖网络。

## 存储结构

使用 SQLite：

```text
runtime/task_state.db
├── tasks：任务状态和最新 Checkpoint 指针
├── task_steps：步骤、验收条件和结果
├── operations：工具执行与幂等记录
└── checkpoints：不可变快照历史
```

Checkpoint 只追加，不覆盖旧记录。运行时数据库不提交 Git。

## Checkpoint 定义

```json
{
  "schema_version": 1,
  "task_id": "checkpoint-exp-001",
  "sequence": 2,
  "task_status": "paused",
  "current_step_id": "step-5",
  "completed_steps": ["step-1", "step-2", "step-3", "step-4"],
  "remaining_steps": ["step-5", "step-6", "step-7", "step-8", "step-9", "step-10"],
  "last_operation_id": "checkpoint-exp-001:step-4:attempt-1",
  "actions_used": 5,
  "actions_limit": 30,
  "next_action": "执行 step-5"
}
```

不保存模型隐藏思维、完整聊天、密钥和大型工具结果正文。

## 状态机

```text
任务：created → running → paused → running → completed / blocked / failed
步骤：todo → in_progress → done / failed / blocked
操作：pending → succeeded / failed / unknown
```

`unknown` 表示工具可能已成功，但程序在确认前崩溃；恢复时必须核查，不能盲目重试。

## 保存时机

- Plan 创建并验证后
- 子任务完成并通过验收后
- 单轮预算用完、准备暂停时
- 请求授权或补充信息前
- 发生可恢复错误时

普通推理和没有状态变化的模型输出不创建 Checkpoint。

## 实验一：正常暂停与恢复

1. 创建 10 步任务，单轮最多执行 5 个行动。
2. 完成前几个步骤后保存 `paused` Checkpoint。
3. 清空进程内任务变量。
4. 从 SQLite 加载最新 Checkpoint。
5. 从 `current_step_id` 继续执行。
6. 汇总结果并标记 `completed`。

预期：完成步骤不重复，全局 `actions_used` 不归零，最终结果与不中断执行一致。

## 实验二：服务重启恢复

执行到暂停点后正常停止并重启 Web 服务，再用同一 `task_id` 继续。

预期：恢复不依赖原 Python 内存；即使会话记忆清空，也能恢复任务状态、当前步骤和剩余预算。

## 实验三：崩溃窗口

| 崩溃位置 | 恢复策略 |
| --- | --- |
| 写入 `pending` 前 | 视为从未开始，可以执行 |
| `pending` 提交后、工具执行前 | 无副作用工具可以安全重试 |
| 工具成功后、写入 `succeeded` 前 | 标记 `unknown`，先核查外部结果 |
| `succeeded` 后、Checkpoint 前 | 使用已保存结果重建 Checkpoint |

## 实验四：幂等恢复

操作 ID 使用：

```text
{task_id}:{step_id}:attempt-{n}
```

重复提交同一 `operation_id` 时：已成功则返回原结果；仍在执行则返回当前状态；参数哈希不同则拒绝复用。

## 实验五：并发覆盖

让两个线程同时读取 `tasks.version=3` 并更新任务。SQL 使用 `WHERE version=3` 乐观锁。

预期：只有一个更新成功；另一个必须重新读取，不能覆盖新状态，也不能生成重复 sequence。

## 实验六：Checkpoint 损坏回退

创建至少 3 个 Checkpoint，修改最新 `snapshot_json` 使校验和不匹配，然后恢复。

预期：识别损坏，回退到最近有效版本，任务进入 `paused` 并记录警告。

## 实验七：产物丢失

Checkpoint 保存产物路径和 SHA-256，分别测试文件正常、被删除和被修改。

只有文件存在且校验和一致时才能保留 `done`；其余情况需要重新验证。

## 实验八：上下文对照

| 组别 | 恢复输入 | Prompt Token | 是否重复执行 | 最终结果 |
| --- | --- | ---: | --- | --- |
| A | 完整 Action、Observation 和会话历史 | | | |
| B | 目标、计划摘要、最新 Checkpoint、当前步骤证据 | | | |

验证 B 组是否用更少 Token 正确恢复。

## SQLite 可靠性配置

```sql
PRAGMA foreign_keys = ON;
PRAGMA journal_mode = WAL;
PRAGMA synchronous = FULL;
PRAGMA busy_timeout = 5000;
```

Checkpoint 插入、任务指针更新和版本递增必须处于同一事务中，任一步失败都整体回滚。

## 评价指标

| 指标 | 判定方式 |
| --- | --- |
| 恢复准确率 | 是否从正确步骤继续 |
| 重复执行次数 | 已完成步骤被再次执行的次数 |
| 状态丢失次数 | 已提交状态在恢复后消失的次数 |
| 并发覆盖次数 | 后写请求错误覆盖新状态的次数 |
| 损坏检测率 | 被篡改 Checkpoint 被识别的比例 |
| 回退成功率 | 能否恢复最近有效版本 |
| 结果一致性 | 中断恢复与不中断基线是否一致 |
| Token 节省 | Checkpoint 组相对完整会话组的降幅 |

## 通过标准

1. 服务重启后可以恢复最新有效 Checkpoint。
2. 已完成步骤不会重复执行。
3. 单轮预算用完只暂停，不清空全局进度。
4. 全局预算跨轮累计，不被 Checkpoint 重置。
5. 并发更新不会相互覆盖。
6. 最新快照损坏时可以回退。
7. 产物异常不会被误判为完成。
8. Checkpoint 恢复的 Prompt Token 少于完整会话恢复。
9. 中断恢复后的最终结果与不中断执行一致。

## 实施顺序

1. 定义 Schema 和状态机。
2. 创建 SQLite 表和事务接口。
3. 实现正常暂停与恢复。
4. 增加 operation_id 和幂等检查。
5. 增加 version 乐观锁。
6. 增加校验和、版本回退和产物校验。
7. 最后接入 `vllm_chat.py` 并对比 Token。

## 最终产出

- SQLite 表结构和 Checkpoint Schema
- 任务状态机
- 8 个恢复与故障注入实验结果
- 完整会话与 Checkpoint 恢复的 Token 对照表
- 当前项目是否需要长期任务层的结论
