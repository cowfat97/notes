# Agent 记忆注入与上下文预算实验

## 实验背景

记忆库可以长期保存大量对话、事实、偏好、决定、事件、文档摘要和任务状态，但模型每次只能看到本轮请求中实际注入的内容。

因此，记忆系统不能只解决“存了什么”，还必须解决：

- 当前问题应该召回哪些记忆？
- 多条记忆发生冲突时采用哪一条？
- 检索结果过长时如何缩减，而不丢失精确事实？
- 如何避免把历史事件误认为当前状态？
- 记忆被压缩后，如何恢复原始证据？
- 工具、记忆、最近对话和 checkpoint 如何竞争同一个上下文窗口？

本实验只研究记忆从存储到本轮上下文的注入过程，不修改模型参数，也不把历史摘要当作唯一事实来源。

## 实验目标

验证以下记忆链路能否在固定 Token 预算内保持事实准确、时间有效和来源可追溯：

```text
完整记忆库
→ 检索候选
→ MemoryItem 标准化
→ 相关性排序
→ 去重与冲突消解
→ 生成有限预览
→ Token 预算装配
→ 注入本轮 messages
→ 按需召回原文
```

重点回答：

1. 限制记忆条数是否足以限制上下文长度？
2. 固定 MemoryItem 字段能否避免精确事实在文本裁剪中丢失？
3. 新旧记忆冲突时，程序能否识别当前有效状态？
4. 结构化事实与自然语言摘要分别应该承担什么职责？
5. 记忆总预算设置为多少时，准确率与 Token 成本最平衡？
6. 被省略的原始内容能否通过 `memory_id` 恢复？

## 核心假设

记忆存储与上下文注入是两个不同阶段：

```text
记忆存储：尽量完整、长期、可追溯
上下文注入：有限、相关、当前有效、符合 Token 预算
```

记忆内容存在数据库或文件中，不代表模型本轮已经看到。只有被组装进 `messages` 的记忆才参与推理。

## 标准 MemoryItem 协议

每条候选记忆先转换为统一结构：

```json
{
  "id": "memory_123",
  "memory_type": "decision",
  "summary": "本地学习模型统一使用 Qwen3",
  "facts": [
    {
      "name": "learning_model",
      "value": "Qwen3",
      "status": "active",
      "valid_from": "2026-09-12",
      "valid_to": null
    }
  ],
  "content": "用户确认以后统一启动 Qwen3，并以 Qwen3 作为学习模型。",
  "source": {
    "type": "conversation",
    "session_id": "session_001",
    "message_id": "message_029"
  },
  "time": {
    "created_at": "2026-09-12T10:30:00+08:00",
    "event_at": "2026-09-12T10:30:00+08:00",
    "expires_at": null
  },
  "score": {
    "relevance": 0.91,
    "importance": 0.80,
    "recency": 0.70
  },
  "artifact": {
    "id": "memory_artifact_123",
    "path": "memory/memory_123.json"
  }
}
```

### 固定保留字段

| 字段 | 作用 | 策略 |
| --- | --- | --- |
| `id` | 记忆唯一标识 | 必须保留 |
| `memory_type` | 记忆类型 | 必须保留 |
| `facts` | 精确事实 | 优先完整保留 |
| `source` | 证据来源 | 必须保留最小引用 |
| `time` | 创建、发生和失效时间 | 必须保留相关时间 |
| `summary` | 简短语义概括 | 限制长度后保留 |
| `score` | 检索和排序依据 | 只保留关键分数 |
| `content` | 原始自然语言内容 | 根据预算缩减或移除 |
| `artifact` | 原文恢复入口 | 必须保留 |

上下文预算不足时，优先缩减 `content`，不能先删除 `facts`、时间和来源。

## 记忆类型

第一阶段支持：

```text
fact        精确事实
preference  用户偏好
decision    已作决定
event       已发生事件
procedure   操作经验
summary     历史摘要
document    文档或材料
checkpoint  长任务执行状态
```

不同类型使用不同预览策略：

- `fact`：保留结构化字段和值。
- `preference`：保留当前有效状态和强度，避免把临时偏好当成永久规则。
- `decision`：保留结论、生效时间、替代关系和必要原因。
- `event`：明确事件发生时间，禁止直接转写成当前状态。
- `procedure`：保留前置条件、步骤摘要和结果。
- `summary`：仅承担历史脉络压缩，不作为精确事实的唯一来源。
- `document`：只注入相关片段，完整文档通过引用召回。
- `checkpoint`：保留目标、已完成、未完成、产物和恢复位置。

## 记忆预算规则

不能只限制记忆条数，因为不同记忆长度差异很大。实验同时限制：

```text
检索候选上限：30 条
排序去重后上限：8 条
单条记忆预览上限：300 Token
全部记忆注入预算：1,500 Token
```

以上数值作为第一轮基线，后续测试：

```text
总预算：500 / 1000 / 1500 / 2500 Token
条数上限：3 / 5 / 8 / 12 条
```

装配时使用与 Qwen3 一致的 Tokenizer 做最终计数：

```python
selected = []

for memory in ranked_memories:
    preview = build_memory_preview(memory)
    preview = shrink_to_item_budget(preview)

    if token_count(selected + [preview]) <= memory_budget:
        selected.append(preview)
```

如果剩余预算不足，不允许在字符串中间截断 JSON；应跳过该项、进一步降级预览或仅保留 `id + facts + source + artifact`。

## 候选检索与排序

第一阶段采用可解释的混合排序：

```text
final_score
= relevance × 0.45
+ importance × 0.20
+ recency × 0.15
+ type_priority × 0.10
+ source_confidence × 0.10
```

其中：

- `relevance`：与当前问题的语义或关键词相关度。
- `importance`：写入记忆时的长期重要程度。
- `recency`：时间衰减结果，不代表越新一定越正确。
- `type_priority`：精确事实和决定通常高于普通摘要。
- `source_confidence`：用户明确陈述、系统事实、模型推断分别赋予不同可信度。

排序后仍要进行去重、冲突检测和预算装配，不能直接取 Top-K 注入。

## 去重规则

以下记忆视为可能重复：

- `facts.name` 相同且值相同。
- 来源指向同一条原始消息。
- 文本高度相似。
- 摘要是原始记忆的派生内容。

重复时优先保留：

```text
结构化事实
→ 原始来源
→ 更新版本
→ 摘要副本
```

摘要不得覆盖或替代精确原始事实。

## 冲突消解规则

示例：

```json
[
  {
    "name": "learning_model",
    "value": "Qwen2.5",
    "valid_from": "2026-08-01"
  },
  {
    "name": "learning_model",
    "value": "Qwen3",
    "valid_from": "2026-09-12"
  }
]
```

不能只按相似度选择，也不能把两条并列交给模型猜测。程序先判断：

1. 两条事实是否描述同一属性。
2. 是否存在明确的替代、撤销或失效关系。
3. 用户询问的是当前状态还是历史状态。
4. 来源可信度是否一致。
5. 时间字段表示记录时间、事件时间还是生效时间。

生成供模型使用的冲突结果：

```json
{
  "current": {
    "learning_model": "Qwen3",
    "source_memory_id": "memory_new"
  },
  "superseded": [
    {
      "learning_model": "Qwen2.5",
      "source_memory_id": "memory_old"
    }
  ],
  "resolution": "newer_explicit_decision"
}
```

无法确定时不自动合并，向模型明确提供冲突标记；高风险任务应请求用户确认。

## 记忆预览降级等级

### Level 0：完整候选记忆

固定字段和完整 `content` 全部保留，适用于短记忆。

### Level 1：限制自然语言内容

保留固定字段，`content` 缩减为有限片段。

### Level 2：移除 content

仅保留：

```text
id + memory_type + facts + summary + source + time + artifact
```

### Level 3：事实卡片

仅保留：

```text
id + memory_type + facts + valid time + source ID + artifact ID
```

### Level 4：不注入，保留可检索状态

当前预算不足且优先级较低时，不把该记忆放入本轮上下文。需要时通过检索或召回工具重新获取。

## 记忆召回接口

按 ID 恢复原始记忆：

```json
{
  "op": "recall_memory",
  "memory_id": "memory_123"
}
```

按事实或时间范围查询：

```json
{
  "op": "search_memory",
  "query": "当前学习模型",
  "memory_types": ["fact", "decision"],
  "valid_at": "2026-09-25",
  "limit": 5
}
```

召回结果仍然转换为 MemoryItem，并受到单条和总 Token 预算限制，避免召回过程再次撑爆上下文。

## 实验分组

| 组别 | 记忆注入策略 |
| --- | --- |
| A | 检索到的记忆全部注入 |
| B | 只限制 Top-K 条数，不限制 Token |
| C | Top-K 后按文本长度截断 |
| D | 标准 MemoryItem + 去重冲突消解 + Token 预算 + 原文召回 |

四组使用相同记忆库、问题、模型参数和检索候选集合。为了隔离变量，第一轮实验固定候选检索结果，只比较候选进入上下文后的处理策略；第二轮再加入真实检索，评估完整链路。

## 测试用例

### 用例一：短而精确的事实

记忆：模型端口是 `8001`。

问题：模型服务端口是什么？

目标：验证所有策略都能完成基础召回，确认实验环境正常。

### 用例二：同一属性的新旧冲突

记忆：

```text
早期：学习模型为 Qwen2.5。
最新决定：以后统一使用 Qwen3。
```

分别提问：

```text
当前使用什么学习模型？
最开始使用什么模型？
模型是什么时候变更的？
```

目标：验证系统能区分当前状态、历史状态和变更时间。

### 用例三：历史事件与当前状态

记忆：昨天 vLLM 服务启动成功，之后已经停止。

问题：

```text
昨天是否成功启动？
现在服务是否仍在运行？
```

目标：防止把历史事件误认为实时状态；当前运行状态应通过工具重新检查，而不是只依赖记忆。

### 用例四：大量无关记忆干扰

插入 100 条与问题无关的记忆，只保留 3 条相关事实。比较各组的 Token、准确率和无关信息引用率。

### 用例五：单条超长记忆

一条记忆包含数千 Token 文档，目标事实位于尾部。D 组通过结构化 `facts` 或 artifact 召回回答，C 组可能因文本截断漏失。

### 用例六：重复记忆

同一事实以原始对话、摘要、自动事实卡三种形式保存。验证 D 组不会将同一事实重复注入三次。

### 用例七：摘要失真

构造摘要将端口 `8001` 错写为 `8081`，原始事实仍为 `8001`。验证精确事实和原始来源优先于派生摘要。

### 用例八：否定与撤销

```text
旧记忆：允许自动删除旧模型。
新记忆：不要删除其他版本模型。
```

验证否定、撤销和替代关系不会在压缩中丢失。

### 用例九：Checkpoint 与普通记忆

长任务存在一个最新 checkpoint，同时记忆库保留多个旧阶段摘要。验证恢复任务时最新 checkpoint 优先，但历史证据仍能按需召回。

### 用例十：预算竞争

在同一请求中同时加入：

- System Prompt
- 当前用户问题
- 最近对话
- 记忆候选
- 工具结果
- Checkpoint

分别测试记忆预算 500、1000、1500、2500 Token，观察记忆准确率是否提高，以及是否挤压当前问题和工具证据。

## 实验步骤

1. 定义 MemoryItem JSON Schema。
2. 准备包含事实、偏好、决定、事件、摘要、文档和 checkpoint 的固定记忆集。
3. 为每条记忆保留原始内容、结构化事实、来源和时间。
4. 建立带标准答案的问题集。
5. 第一轮固定检索候选，分别执行 A、B、C、D 四种注入策略。
6. 每次模型调用前记录实际注入的 MemoryItem、排序、冲突决议和 Token 数。
7. 每个用例至少重复 5 次，生成参数固定为 `temperature=0`。
8. 第二轮启用真实检索，额外记录 Recall@K 和候选缺失率。
9. 对需要原文的任务触发 `recall_memory`，记录召回次数和附加 Token。
10. 比较准确率、上下文成本、冲突误判和召回开销。

## 记录指标

| 指标 | 说明 |
| --- | --- |
| Recall@K | 目标记忆是否进入候选集合 |
| 注入命中率 | 目标记忆是否实际进入本轮上下文 |
| 事实准确率 | 精确值、名称、时间是否回答正确 |
| 当前状态准确率 | 是否选择当前有效事实 |
| 历史状态准确率 | 是否能回答旧状态而不与当前状态混淆 |
| 冲突识别率 | 冲突记忆是否被程序标记和正确处理 |
| 重复注入率 | 相同事实是否被重复放入上下文 |
| 来源可追溯率 | 回答是否能对应 memory/source ID |
| 记忆 Token | 所有记忆实际占用的输入 Token |
| 总 Prompt Token | 本轮完整请求 Token |

| 召回附加轮数 | 完成回答增加的工具调用次数 |

## 验收标准

D 组应满足：

1. 目标记忆已经进入候选时，关键 `facts` 注入保留率为 100%。
2. 当前状态、历史状态和事件时间能够明确区分。
3. `id`、来源、有效时间和 artifact 引用不会被自然语言裁剪破坏。
4. 注入记忆总 Token 不超过配置预算。
5. 重复记忆不会重复占用上下文。
6. 存在冲突但无法确定时，系统明确标记冲突，不静默选择。
7. 原始记忆能通过 `memory_id` 恢复，且内容校验一致。
8. 召回结果仍受预算约束，不导致二次上下文溢出。
9. 与 A、B、C 组相比，在更少 Token 下保持相同或更高事实准确率。

## 与工具输出实验的关系

`3.4_统一工具输出与上下文预算实验.md` 解决工具结果的问题，本实验解决长期记忆注入的问题。二者可以共享：

```text
统一 ContextItem 基础协议
Token 计数器
artifact 存储
召回接口
全局上下文预算器
```

但不能使用完全相同的 Adapter：

```text
工具输出：优先保留状态、错误、summary、artifact，缩减 data
记忆结果：优先保留 facts、时间、来源、artifact，缩减 content
```

后续综合实验需要把最近对话、工具结果、记忆、上传内容和 checkpoint 同时放入一个全局预算中，验证它们之间的动态分配。
