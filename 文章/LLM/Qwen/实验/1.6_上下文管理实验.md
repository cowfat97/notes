# 上下文管理实验

## 实验目的

理解大语言模型如何利用上下文，以及上下文长度、历史裁剪和记忆检索如何影响回答结果。

本实验重点回答：

- 模型在一次生成中实际看到了什么
- 上下文和程序保存的记忆有什么区别
- 多轮对话为什么会越来越慢
- 为什么不能无限发送全部历史
- 滑动窗口、记忆检索和摘要压缩分别解决什么问题

## 核心概念

模型本身不会永久记住之前发生的对话。每次调用模型时，它只能根据本次请求携带的内容生成答案。

```text
Session Memory 保存历史
        ↓
程序选择本轮需要的消息
        ↓
messages 作为上下文发给模型
        ↓
模型在 Context Window 内生成答案
```

因此需要区分：

```text
记忆：程序长期或临时保存的数据
上下文：本次请求真正发送给模型的数据
```

记忆中存在一条信息，不代表模型当前一定能看到它。只有被选入 `messages` 的内容，才会参与本次推理。

## 当前项目中的上下文链路

当前 `qwen_chat.py` 的主要链路：

```text
remember(user_text)
  → 保存当前用户消息

as_list()
  → 取得准备发送给模型的消息

模型生成
  → 根据当前上下文产生 ActionOutput

record(turns)
  → 保存模型输出

inject(observation)
  → 将工具执行结果加入上下文
```

一次完整的 ReAct 记忆检索可能向上下文增加：

```text
用户问题
→ memory_search 行动
→ Observation 检索结果
→ answer 行动
```

如果每轮都发送全部历史，上下文会持续增长。

## Token 预算

一次请求需要满足：

```text
输入 Token + 最大输出 Token ≤ max-model-len
```

例如 vLLM 使用：

```text
--max-model-len 4096
```

并设置：

```text
max_tokens=512
```

那么系统提示、历史消息、Observation 和当前问题应尽量控制在约 3584 Token 以内。实际还要考虑 Chat Template 增加的特殊 Token，不能把 4096 全部分配给可见文本。

## 实验一：模型实际看到了什么

### 目的

观察普通回答和记忆检索时，发送给模型的 `messages` 有什么差异。

### 测试 A：普通回答

输入：

```text
什么是 vLLM？
```

预期链路：

```text
用户问题
→ action=answer
→ 结束
```

### 测试 B：记忆检索

第一轮输入：

```text
我喜欢羽毛球。
```

第二轮输入：

```text
我之前说过喜欢什么运动？
```

预期链路：

```text
用户问题
→ action=memory_search
→ 执行 search("运动")
→ 注入 Observation
→ 再次调用模型
→ action=answer
```

### 观察方式

在每次模型调用前记录：

```python
for index, message in enumerate(turns):
    logger.info(
        "context[%d] role=%s content=%r",
        index,
        message["role"],
        message["content"],
    )
```

记录：

| --- | --- | --- |
| 模型调用次数 | | |
| 输入消息数 | | |
| 是否包含 Observation | | |
| 最终 action | | |
| 总耗时 | | |

### 结论问题

- 模型第一次调用时能否直接看到检索结果？
- Observation 是如何进入第二次模型调用的？
- 如果不调用 `inject()`，第二次模型调用会缺少什么？

## 实验二：上下文增长的代价

### 目的

观察连续多轮对话后，消息数量、Token 数和响应时间如何变化。

### 实验步骤

连续进行 10 轮对话，每轮都让模型回答一个简短问题：

```text

第 3 轮：什么是上下文窗口？
第 4 轮：什么是 KV Cache？
第 5 轮：什么是 Prompt？
```

## 实验三：完整历史与滑动窗口

### 目的

比较发送全部历史与只发送最近消息时，回答质量和性能的变化。

### 实验分组

#### A 组：完整历史

```text
System Prompt
+ 全部历史消息
+ 当前问题
```

#### B 组：滑动窗口

```text
System Prompt
+ 最近 6 条消息
+ 当前问题
```

#### C 组：滑动窗口加相关记忆

```text
System Prompt
+ 检索到的相关历史
+ 最近 6 条消息
+ 当前问题
```

### 测试数据

在第一轮写入一个唯一事实：

```text
我的实验代号是蓝鲸 47。
```

继续进行至少 8 轮无关对话，最后提问：

```text
我最开始告诉你的实验代号是什么？
```

### 预期

| 分组 | 预期表现 |
| --- | --- |
| A：完整历史 | 能回答“蓝鲸 47”，但输入 Token 最多 |
| B：最近 6 条 | 早期事实被裁掉，应该无法可靠回答 |
| C：窗口 + 检索 | 检索回早期事实，并以较少上下文正确回答 |

## 实验四：上下文溢出

### 目的

验证上下文接近或超过服务上限时，系统能否提前处理，而不是等 vLLM 返回错误。

### 实验步骤

逐步增加输入长度：

```text
约 1000 Token
约 2000 Token
约 3000 Token
接近服务上限
明确超过服务上限
```

固定：

```text
max_tokens=512
temperature=0
```

观察：

- 是否得到 HTTP 4xx
- 错误信息是否明确
- EngineCore 是否保持健康
- 失败请求是否写入 Session Memory
- 下一次正常请求能否继续执行

### 正确处理策略

```text
计算本轮 Token 预算
→ 保留 System Prompt
→ 保留当前用户问题
→ 优先保留相关记忆
→ 裁剪无关旧消息
→ 必要时压缩历史摘要
→ 仍然超限则明确拒绝
```

不能静默截断当前问题，也不能在失败后把半条 assistant 输出写入记忆。

## 上下文管理策略对比

| 策略 | 优点 | 缺点 | 适用场景 |
| --- | --- | --- | --- |
| 全部历史 | 实现简单、信息完整 | Token 持续增长 | 短对话、实验基线 |
| 滑动窗口 | 成本稳定、速度可控 | 容易遗忘早期事实 | 连续但局部相关的对话 |
| 记忆检索 | 只取相关信息 | 检索可能漏召回 | 长期事实与跨轮回忆 |
| 摘要压缩 | 保留整体脉络 | 摘要可能丢细节 | 长会话阶段性压缩 |
| 混合策略 | 质量与成本平衡 | 实现复杂 | 正式业务系统 |

推荐的长期结构：

```text
System Prompt
+ 历史摘要
+ 相关记忆检索结果
+ 最近若干轮原始对话
+ 当前用户问题
```

## 判定标准

实验完成后，应能证明：

1. 可以打印并解释每次模型调用的完整上下文。
2. 可以区分 Session Memory 与实际发送的 `messages`。
3. 可以量化上下文增长对 Token 和延迟的影响。
4. 可以说明滑动窗口为什么会遗忘早期信息。
5. 可以通过相关记忆检索恢复被裁剪的重要事实。
6. 超限请求不会导致服务崩溃或污染记忆。

## 最终产出

- 普通回答和记忆检索两条上下文链路日志
- 10 轮对话的 Token 与延迟增长曲线
- 完整历史、滑动窗口、窗口加检索的对照表
- 一份适合当前项目的上下文组装规则
- 下一阶段是否需要引入自动摘要压缩的结论
